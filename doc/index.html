01 — Project Overview

Equipify is a multi-platform equipment rental marketplace that connects equipment owners with renters in a trust-verified environment. Inspired by the Airbnb model, the platform enables individuals and businesses to list, discover, and rent equipment across diverse categories — from electronics and vehicles to fitness machines and real estate.

The system operates across three client platforms: a React-based web application served on port 5173, a Flutter mobile application for Android and iOS, and a RESTful ASP.NET Core 8.0 Web API backend on port 5000. All platforms communicate via HTTP/REST using JSON as the data interchange format, with multipart form-data for file uploads.

Key Features

  • Bilingual Support: Full Arabic (RTL) and English (LTR) interface across all platforms, with 214 translation keys on the web and 130+ on mobile.
  • Phone-Based Authentication: Registration and login via phone number with OTP verification, JWT access tokens, and refresh token rotation.
  • Interactive Maps: Leaflet-based map browsing on web, flutter_map on mobile, with geographic viewport filtering and click-to-place-pin for listing locations.
  • Dynamic Pricing: Five rental units (hour, day, week, month, year) with corresponding cost fields and duration constraints.
  • Admin Moderation: Listing approval workflow, user management, category management, and aggregate dashboard statistics.
  • Rating System: 1–5 star ratings on completed rentals with owner average recalculation.

02 — Problem Statement

The equipment rental market faces several persistent challenges that reduce efficiency and trust between parties:

  • Fragmented Discovery: Equipment owners and renters rely on word-of-mouth, social media groups, or scattered classified ads. There is no centralized, searchable platform that aggregates rental equipment by category, location, price, and availability.
  • Trust Deficit: Without a verification mechanism, renters have no way to assess the reliability of an owner, and owners cannot verify the identity or intentions of renters. This leads to hesitation and failed transactions.
  • Manual Scheduling Conflicts: Without an integrated booking system, overlapping rental requests are common, resulting in double-bookings and disputes.
  • Lack of Transparency: Pricing, availability, and equipment condition are often unclear. Renters may encounter hidden fees or receive equipment that does not match the description.
  • No Accountability: Without a rating or review system, there is no mechanism to reward reliable owners and renters or to flag problematic participants.
  • Limited Language Support: Most existing platforms serve only English-speaking users, excluding Arabic-speaking populations who constitute a significant market segment.

Equipify addresses these challenges through a purpose-built, bilingual marketplace with verified identities, integrated booking with OTP confirmation, transparent pricing, and a community-driven rating system.

03 — Proposed Solution

Equipify provides a comprehensive, multi-platform solution that addresses each identified problem through the following architectural and functional decisions:

Centralized Marketplace

A unified platform where equipment owners can create detailed listings with images, pricing, location coordinates, and availability windows. Renters can browse, search, filter, and discover equipment through both grid and map views.

Verified Identity System

All user interactions require phone-based registration with OTP verification. This ensures that every participant on the platform has a verified phone number, establishing a baseline of accountability and traceability.

Integrated Booking Engine

The rental request workflow enforces date/time selection, automatic cost calculation, overlap detection against existing bookings, and OTP-verified confirmation. This eliminates double-bookings and provides a clear audit trail.

Admin Moderation Layer

All new listings enter a Pending state and require admin approval before becoming visible in the marketplace. Admins can approve, deactivate, or delete listings, and can block or unblock users, ensuring content quality and platform integrity.

Community Trust Mechanism

After a completed rental, the renter can submit a 1–5 star rating. The system enforces one rating per rental request and recalculates the owner's average rating in real time, creating a transparent reputation system.

Bilingual Architecture

The entire user interface — including navigation, forms, error messages, and notifications — supports Arabic (default) and English with full RTL layout support. Categories include a NameAr field for bilingual display.

04 — Objectives

The primary objectives of the Equipify project are:

  1. Build a Cross-Platform Marketplace: Develop a web application (React + TypeScript), a mobile application (Flutter + Dart), and a backend API (ASP.NET Core 8.0) that function as a cohesive equipment rental ecosystem.
  2. Implement Secure Authentication: Provide phone-based registration with OTP verification, JWT access tokens with configurable expiry (60 minutes for users, 120 minutes for admins), and refresh token rotation with 7-day expiry.
  3. Enable Equipment Listing Management: Allow authenticated users to create, edit, activate/deactivate, and delete equipment listings with image upload (maximum 6 images, 5MB each), map-based location selection, and dynamic pricing based on five rental units.
  4. Provide Advanced Search and Discovery: Implement text-based search across title, description, location, and owner name; category and price filtering; rental unit and duration filtering; geographic viewport filtering via map bounds; and paginated results (maximum 50 per page).
  5. Enforce a Booking Workflow: Implement a rental request lifecycle with OTP verification, overlap detection, owner accept/reject, and post-rental rating.
  6. Support Administrative Oversight: Provide an admin dashboard with aggregate statistics, listing moderation (approve/deactivate), user management (block/unblock/delete), and category CRUD.
  7. Deliver Bilingual UX: Support Arabic and English with RTL/LTR layout switching, bilingual category names, and locale-aware date/number formatting.
  8. Ensure Security Best Practices: Apply BCrypt password hashing, timing-attack mitigation, rate limiting, input validation, file upload security (extension whitelist, magic byte verification, GUID filenames), and security headers.

06 — Target Users

The system defines three primary roles, each with distinct access levels and capabilities:

RoleAccess LevelCapabilities
Guest Public (unauthenticated) Browse listings, view listing details, view categories, search and filter, view map markers
User Authenticated (JWT + role: User) All Guest capabilities, plus: create/edit/delete own listings, send rental requests, accept/reject incoming requests, rate owners after completed rentals, edit profile, change password
Admin Authenticated (JWT + role: Admin) View dashboard statistics, approve/deactivate/delete any listing, block/unblock/delete users, create/edit/delete categories, view/delete all rental requests

User Personas

  • Equipment Owner (User): An individual or business that owns equipment (tools, vehicles, electronics) and wants to generate income by renting it out. They create listings, manage availability, and respond to rental requests.
  • Renter (User): A person who needs equipment temporarily — for a project, event, or short-term use. They search for equipment, compare options, and submit rental requests with OTP verification.
  • Platform Administrator (Admin): A trusted operator who ensures marketplace quality by reviewing listings, managing user accounts, and maintaining categories.

07 — Functional Requirements

FR-01: User Registration and Authentication

  • The system shall allow users to register using a phone number, first name, last name, email address, and password.
  • The system shall send an OTP to the provided phone number before completing registration.
  • The system shall hash passwords using BCrypt before storage.
  • The system shall issue a JWT access token (60-minute expiry) and a refresh token (7-day expiry) upon successful login.
  • The system shall support admin login via username and password with a separate 120-minute JWT (no refresh token).
  • The system shall provide a forgot-password flow using OTP verification.

FR-02: Equipment Listing Management

  • Authenticated users shall be able to create listings with title, description, category, location (address + latitude/longitude), rental unit, pricing, and images.
  • The system shall accept five rental units: hour, day, week, month, year.
  • The system shall accept up to 6 images per listing (5MB max, .jpg/.jpeg/.png/.gif/.webp).
  • New listings shall enter Pending status and require admin approval before becoming visible.
  • Owners shall be able to activate/deactivate their own listings.
  • Editing a listing shall revert its status to Pending for re-review.

FR-03: Search and Discovery

  • The system shall support text search across listing title, description, location address, and owner name (case-insensitive).
  • The system shall support filtering by category, price range, rental unit, and duration range.
  • The system shall support geographic viewport filtering via map bounds (west/south/east/north).
  • The system shall return paginated results with a maximum of 50 items per page.

FR-04: Rental Request Lifecycle

  • Authenticated users shall be able to send a rental request for a listing with date range and time range.
  • The system shall require OTP verification before creating a rental request.
  • The system shall detect and prevent overlapping rental requests for the same listing.
  • The listing owner shall be able to accept or reject incoming requests.
  • The renter shall be able to cancel their own request.

FR-05: Rating System

  • After an accepted rental, the renter shall be able to submit a 1–5 star rating for the owner.
  • The system shall enforce one rating per rental request (unique constraint).
  • The system shall recalculate the owner's average rating upon each new rating submission.

FR-06: Admin Operations

  • The admin shall be able to view aggregate dashboard statistics (total users, listings, active listings, pending listings, categories, requests, pending requests).
  • The admin shall be able to approve or deactivate any listing.
  • The admin shall be able to block/unblock or delete any user.
  • The admin shall be able to create, update, and delete categories (with bilingual names).
  • The admin shall be able to view and delete any rental request.

FR-07: Internationalization

  • The system shall default to Arabic (RTL) and support switching to English (LTR).
  • The web application shall provide 214 translation keys; the mobile application shall provide 130+ translation keys.
  • The system shall persist the user's language preference in localStorage (web) or SharedPreferences (mobile).

08 — Non-Functional Requirements

NFR-01: Security

  • Passwords shall be hashed using BCrypt with auto-generated salt.
  • The system shall implement timing-attack mitigation by running BCrypt even for unknown phone numbers.
  • JWT tokens shall use HMAC-SHA256 signing with a configurable secret key.
  • Refresh tokens shall be stored as SHA-256 hashes with a unique index.
  • The system shall enforce rate limiting: 10 requests/minute on auth endpoints, 5 requests/minute on OTP endpoints.
  • File uploads shall be validated against extension whitelist, Content-Type, and magic bytes.
  • The system shall set security headers: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer.

NFR-02: Performance

  • The web application shall be built with Vite for fast development and optimized production builds.
  • All pages shall be lazy-loaded via React.lazy() and Suspense.
  • The API shall use Entity Framework Core with compiled queries for hot paths.
  • Images shall be served as static files from wwwroot/uploads/.

NFR-03: Reliability

  • All business logic shall return ServiceResult instead of throwing exceptions.
  • Global exception handling shall convert exceptions to RFC 7807 ProblemDetails responses.
  • The database shall use foreign key constraints with appropriate delete behaviors (Cascade, Restrict).

NFR-04: Usability

  • The interface shall support full Arabic/English bilingual display with RTL/LTR layout switching.
  • The design shall follow a consistent visual language with the Inter font family (English) and Cairo (Arabic).
  • The web shall use a glassmorphism-based design system; the mobile shall use Material 3 with custom theming.

NFR-05: Maintainability

  • The backend shall follow Clean Architecture with four layers: Domain, Data, Service, Api.
  • The system shall use the Repository + Unit of Work pattern for data access.
  • All services shall be registered via Dependency Injection (Scoped for most, Singleton for OTP and AdminAuth).

10 — System Architecture

Equipify follows a three-tier architecture with clear separation between presentation, business logic, and data storage layers:

System Architecture Figure 1
Figure 1: Three-Tier System Architecture — Equipify

Client Layer

The client layer consists of two independent applications that communicate with the backend via HTTP/REST:

  • React Web App (port 5173): A single-page application built with React 19, TypeScript 6, and Vite 8. Uses Leaflet for interactive maps and React Context for state management.
  • Flutter Mobile App (Android/iOS): A cross-platform mobile application built with Flutter 3.38 and Dart 3.9. Uses flutter_map for maps and the Provider package for state management.

API Layer

The backend is an ASP.NET Core 8.0 Web API running on Kestrel (port 5000). It exposes 48 RESTful endpoints organized across 6 controllers and implements JWT authentication, rate limiting, and global exception handling.

Data Layer

The data layer consists of SQL Server 2022 (running in Docker container equipify-sql on port 1433) and a local file system for uploaded images under wwwroot/uploads/.

20 — Authentication Flow

The authentication system implements a multi-step flow with JWT access tokens, refresh token rotation, and OTP verification for sensitive operations.

Security Properties

  • BCrypt Timing-Attack Mitigation: BCrypt always runs even for unknown phone numbers, preventing timing-based user enumeration.
  • Refresh Token Rotation: Old tokens are revoked on refresh, and new tokens are issued. SHA-256 hashes are stored in the database.
  • OTP Security: Codes are stored as SHA-256 hashes with 5-minute expiry, 3 max attempts, and 60-second resend cooldown. Fixed code 0000 in development mode.
  • JWT Configuration: HMAC-SHA256 signing, 60-minute user tokens, 120-minute admin tokens, 30-second clock skew tolerance.

Middleware Pipeline

Every incoming request passes through the following middleware in order:

  1. ExceptionHandlingMiddleware: Catches unhandled exceptions and converts them to RFC 7807 ProblemDetails responses.
  2. Rate Limiting: Enforces per-IP throttling (10/min for auth, 5/min for OTP).
  3. JWT Authentication: Validates Bearer tokens using HMAC-SHA256.
  4. CORS: Allows requests from localhost:5173.

27 — Error Handling

The backend implements a global exception handling strategy through ExceptionHandlingMiddleware that converts all unhandled exceptions into standardized RFC 7807 ProblemDetails responses.

ServiceResult Pattern

All service methods return ServiceResult or ServiceResult<T> instead of throwing exceptions. Controllers inspect the Success property and map failures to appropriate HTTP status codes:

ServiceResult { bool Success; string? Error; }
ServiceResult<T> : ServiceResult { T? Value; }

28 — Validation

Input validation is enforced at multiple layers to ensure data integrity and prevent malicious input.

Server-Side Validation

  • Data Annotations: Entity properties use [Required], [MaxLength], [Precision] attributes enforced by EF Core.
  • EF Configurations: Fluent API configurations define unique indexes (PhoneNumber, EmailAddress, TokenHash, RentalRequestId), precision for decimal fields, and delete behaviors.
  • Service Layer: Business rules are validated before persistence (e.g., category existence, listing ownership, overlap detection, OTP verification).

File Upload Validation

  • Extension Whitelist: .jpg, .jpeg, .png, .gif, .webp only.
  • Content-Type Check: MIME type must match expected image types.
  • Magic Byte Verification: File header bytes are validated against known image signatures.
  • Size Limit: Maximum 5MB per file, maximum 6 files per upload.
  • GUID Filenames: User-provided filenames are replaced with GUIDs to prevent path traversal.

Client-Side Validation

  • React: Form validation in Auth.tsx and ListingForm.tsx with real-time feedback.
  • Flutter: Form validation in RegisterScreen and ListingFormScreen with translated error messages.
  • SQL Injection: Prevented by Entity Framework Core's parameterized queries.
  • XSS: Prevented by React's automatic HTML escaping and Flutter's widget-based rendering.

29 — Performance

Frontend Performance

  • Lazy Loading: All pages are loaded via React.lazy() and Suspense, reducing initial bundle size.
  • Vite: Fast HMR in development and optimized production builds with tree-shaking.
  • Image Optimization: Listing images are served as static files from wwwroot/uploads/ with browser caching.
  • Provider-Based State: Minimal re-rendering through targeted Context providers.

Backend Performance

  • Scoped Services: Per-request DI lifetime prevents state leakage and enables efficient resource management.
  • Repository Pattern: Abstracts EF Core queries and enables future query optimization.
  • Pagination: Browse endpoint limits results to 50 per page to prevent large payload transfers.
  • Static File Serving: Images served directly by Kestrel without going through the application pipeline.

Database Performance

  • Unique Indexes: On PhoneNumber, EmailAddress, TokenHash, and RentalRequestId for O(log n) lookups.
  • Appropriate Delete Behaviors: CASCADE for owned data, RESTRICT to prevent accidental cascades.
  • Decimal Precision: Precision(12,2) on all cost fields for efficient storage.

30 — Scalability

The current architecture is designed for single-server deployment. The following areas have been identified for future scalability improvements:

Current Limitations

  • Single Server: API, database, and file storage run on a single machine.
  • In-Memory OTP: OTP codes are stored in a ConcurrentDictionary, which does not survive restarts or scale across instances.
  • Local File Storage: Uploaded images are stored on the local filesystem under wwwroot/uploads/.
  • No Caching Layer: No Redis or distributed cache is implemented.

Scaling Path

  • Horizontal Scaling: The stateless API (except OTP) can be load-balanced behind a reverse proxy.
  • Distributed Cache: Redis could replace the in-memory OTP store and add response caching.
  • Cloud File Storage: Azure Blob Storage or AWS S3 could replace local file storage for images.
  • Database Scaling: Read replicas for browse-heavy workloads, connection pooling via EF Core.
  • Containerization: Dockerfiles for API and frontend would enable consistent deployment across environments.

34 — Conclusion

Equipify successfully demonstrates the design and implementation of a multi-platform equipment rental marketplace that addresses the challenges of fragmented discovery, trust deficits, and manual scheduling in the equipment rental industry.

The system delivers a cohesive experience across three platforms — a React web application, a Flutter mobile application, and an ASP.NET Core backend API — unified by a shared RESTful API, consistent data models, and a bilingual (Arabic/English) user interface.

Key achievements of the project include:

  • A secure authentication system with phone-based OTP verification, JWT tokens, and refresh token rotation.
  • A complete rental lifecycle with OTP-verified booking, overlap detection, owner acceptance, and post-rental rating.
  • An admin moderation layer ensuring marketplace quality through listing approval and user management.
  • A bilingual architecture supporting Arabic and English with full RTL layout switching.
  • An eight-layer security architecture addressing common web application threats.
  • A Clean Architecture backend with 48 API endpoints, 9 services, and a generic repository pattern.

The project establishes a solid foundation for future enhancements including payment integration, real-time messaging, push notifications, and advanced search capabilities. The modular architecture ensures that these additions can be implemented with minimal disruption to existing functionality.
